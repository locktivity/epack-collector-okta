# Changelog

## Unreleased

## v0.5.1

- The collector is built on epack v0.10.5.
- At trust, `diagnostics.warnings` names no Okta user, group, or policy by ID. A warning about one user says "a user", such as `a user: failed to fetch MFA factors`, where it named the user's ID before. A failed call is given by its HTTP status and Okta's error code, such as `okta API returned status 500: E0000009`, or by its failure code, such as `the call failed with timeout`. The error's own text can hold the request's URL and Okta's error summary, which name users, groups, and policies by ID. Audit and internal runs write the same warnings as before.
- The collector result's `targets` says what the run was pointed at: the organization, chosen by `org_domain`, at `org_domain` in `artifacts/okta.details.json`.

## v0.5.0

- The detailed artifact moves from `artifacts/okta.json` to `artifacts/okta.details.json`, and `collect` lists it as `details`. A collector configured under another name in `epack.yaml`, such as `okta-prod`, writes every file under that name, such as `artifacts/okta-prod.details.json` and `artifacts/okta-prod.idp-posture.json`. Two Okta orgs can then go in one pack.
- Every page of each Okta list is read. Okta sends the next page's link in a second `Link` header, and only the first header was read before. Each list stopped after its first page of up to 200 items, so counts and percentages over more users, apps, groups or System Log events covered only the first 200. They now cover every one.
- The System Log read ends at an empty page, since Okta can offer a next page when no events remain.
- An MFA enrollment rule set to `CHALLENGE` no longer counts as an MFA requirement. Under it, people enroll the next time a sign-on rule requires MFA. Okta's default enrollment rule is set to `CHALLENGE`, so `policy.mfa_required_coverage_pct`, `mfa_required_users_count`, `mfa_required_all` and `mfa_required_any` can drop for orgs that kept it.
- The MFA requirement follows Okta's order for policies and rules. A person whose first matching sign-on policy has no rule for them is judged by the next policy. Before, they counted as not required to use MFA. The managed-device counts follow the same order.
- A sign-on rule with a network zone or another condition on how people sign in applies only to the sign-ins that meet it. A person counts as required to use MFA only when their other sign-ins need MFA too. Before, a rule that denied sign-in from one zone made the people it covered read as not required to use MFA.
- `api_tokens.total_active_count` and `recently_used_count` count every token in Okta's list. The list holds only active tokens, and Okta's token object has no status. Both counts read 0 before. Each row of `api_tokens.inventory` has `status` `ACTIVE`.
- `system_log.count_by_category` counts `policy.rule.add`, `zone.create`, `zone.update` and `zone.delete` events. Before, the filter named four event types that Okta does not have, so rules added to policies and network zone changes were not counted.
- OpenID Connect identity providers, such as Google and Microsoft, have an `issuer_host` in `identity_providers.inventory`. It was left out before.
- In `device_access.policies`, `screen_lock_required` and `disk_encryption_required` are false for a device assurance policy that accepts `NONE`. Okta's `NONE` means no screen lock or no encryption is set.
- Inactive apps are left out of the app counts and percentages. Before, an app deactivated in Okta still counted in `apps.total_count` and toward SSO, provisioning and deprovisioning. This changes `posture.sso_coverage`, the counts and percentages in `apps`, and `app_security` in `okta.idp-posture.json`. `apps.inventory` still lists inactive apps.
- A policy rule whose device condition has `managed` or `registered` set to `true` or `false` is read. Okta sends both as booleans. Before, one such rule failed the read of every rule in its policy.
- At internal, `network_zones.inventory` lists the locations and ASNs of enhanced dynamic zones (`DYNAMIC_V2`). Okta sends them as include and exclude lists. Before, each zone's locations and ASNs got an "unexpected shape" warning and a gap. This included the empty lists of `DefaultEnhancedDynamicZone`, which every org has. When a zone also excludes locations or ASNs, that field is still left out with a gap.
- At audit and internal, `privileged_access.custom_roles` is `[]` for an org with no custom admin roles. It was left out before, with no gap.
- In `okta.idp-posture.json`, `privileged_access.privileged_users_count`, `super_admin_count` and `standing_privileged_users_count` are written from the audit level only, as the idp-posture schema now marks them. `privileged_users_present` and `standing_privileged_users_present` are written at every level.
- In `okta.idp-posture.json`, `privileged_mfa_coverage_pct` and `privileged_phishing_resistant_pct` are null for an org with no admins. They were left out before, which reads as a value that could not be collected.
- In `okta.idp-posture.json`, the counts behind each percentage are written from the audit level, as the idp-posture schema marks them. These are `user_security.user_count`, `mfa_user_count`, `phishing_resistant_user_count`, `inactive_user_count` and `locked_out_user_count`, `app_security.app_count`, `sso_app_count`, `provisioning_app_count` and `deprovisioning_app_count`, `privileged_access.privileged_mfa_user_count` and `privileged_phishing_resistant_user_count`, `policy.mfa_required_user_count`, and `lifecycle.account_count` and `suspended_account_count`. `users_present`, `apps_present` and `accounts_present` are written at every level.
- In `okta.idp-posture.json`, `inactive_pct`, `locked_out_pct` and `suspended_pct` round up, as the idp-posture schema says. One person in three reads 34, where it read 33 before. The same values in `okta.json` still round down.
- In `okta.idp-posture.json`, each percentage over an org with no users or no apps is null. It was left out before. Okta has no data on weak passwords, password policy compliance or archived accounts. So `weak_password_pct`, `password_policy_noncompliant_pct` and `archived_pct`, and at the audit level their counts, are left out of every run with an `unsupported` gap. That gap does not make a run partial.
- In `okta.idp-posture.json`, `policy.phishing_resistant_required_for_privileged` is left out with a `not_read` gap. So is `app_security.authorized_third_party_apps_count` at the audit level. Okta reports the first in `ACCESS_POLICY` rules and the second as each user's app grants, and neither is read yet. Both were left out before with no gap. A `not_read` gap does not make a run partial.
- In `okta.idp-posture.json`, `policy.mfa_required`, `mfa_required_coverage_pct` and `mfa_required_user_count` can be left out with a `not_read` gap. This happens when an active app has an app sign-in policy and the sign-on and enrollment policies don't require MFA of everyone. An app sign-in policy can require MFA in its `ACCESS_POLICY` rules, which are not read yet. Before, an org that required MFA only there read `mfa_required` false and `mfa_required_coverage_pct` 0. When the app list can't be read, the three values are left out with its gap. The same values in `okta.details.json` are unchanged.
- Each operation in the collector result lists the OAuth scope its call needs as `permission`, at every level. A `permission_denied` gap names the scope only when the service app asked for it and Okta did not grant it, as before. Okta refuses a missing scope and a missing admin role with the same `E0000006`, so the refusal alone does not show which one is missing.
- The schema gives each field a label and a summary for readers of the pack, as `x-epack-label` and `x-epack-summary`. Each value a trust run writes also has an `x-epack-method` sentence on how it is measured, and the idp-posture values copied from it use the same sentence.
- The schema declares the values of `groups.count_by_source`, `network_zones.count_by_type`, `identity_providers.count_by_protocol` and `system_log.count_by_category` as counts.
- The build file and `--capabilities` list `evidencepack/idp-posture@v1` as the kind of evidence the collector writes.
- With epack v0.10.0, a collector result below the audit level leaves out the tenant and the call and step counts. Its operations gain `retried`, `status_codes` and `error_codes`, and its steps gain `any_failed`, at every level.
- Each percentage, and each of `policy.mfa_required_all` and `device_access.managed_device_required_for_admins`, has the count it is computed from beside it, at every level: `posture.mfa_enrolled_users_count`, `posture.mfa_phishing_resistant_users_count`, `users.password_expired_count`, `users.locked_out_count`, `users.inactive_count`, `users.suspended_count`, `apps.sso_count`, `apps.provisioning_enabled_count`, `apps.deprovisioning_enabled_count`, `privileged_access.privileged_mfa_enrolled_count`, `privileged_access.privileged_phishing_resistant_count`, `policy.mfa_required_users_count` (the count behind both `mfa_required_coverage_pct` and `mfa_required_all`), `device_access.managed_device_required_users_count`, and `device_access.managed_device_required_admins_count`. A count is null, with its percentage's gap, whenever its percentage is left out, and 0 over a population of 0, where the percentage is null.
- The schema names each percentage's count with `x-epack-numerator` and its rounding with `x-epack-rounding: floor`, so the SDK checks that every percentage is `floor(100 × count ÷ population)`. The status-based user counts and `users.total_count` name the inventory rows they count, and the output check recounts them at audit and internal unless the inventory was cut short.
- At internal, each row of `users.inventory` and `privileged_access.inventory` has `has_active_mfa` and `has_phishing_resistant_mfa`, which restate the person's factor list. They are left out, with a gap, when the person's factors could not be read. Audit-level rows are unchanged, and carry no per-person MFA status.
- The collector result lists the run's 14 steps, from `sign_in` to `org_settings`, with the calls each one made. A trust run has the first six: `sign_in`, `people`, `apps`, `admin_roles`, `policies`, and `device_assurance`. Each step prints its title as the run's status line.
- `signed_in_as` records the sign-in method, `private_key_jwt` for a service app or `api_token`, and for a service app the scopes it requested, as `requested_scopes`, and `read_only: true`, since the token carries only the read scopes the collector asks for.
- A `permission_denied` gap names the scope to grant, as `missing_permission`, when the service app asked for it and Okta did not grant it. A refusal with the scope granted names no scope, and its warning now says the service app needs an admin role that can read the surface. A refusal under an API token names no scope, and its warning names the token owner's admin role. The 403 warnings in `diagnostics.warnings` change to match, including those for API tokens, admin-role assignments, and custom admin roles.
- Every gap carries the warning the collector wrote for it, shown at audit and internal, and names the call that left the value out, by `operation` and `call`, and the line that recorded it, as `source`. Errors the Okta client builds from a response, such as a body it cannot decode, name that response's call too.
- The result's request rows carry Okta's `errorCode` for each failed response as `vendor_code`, such as `E0000047` for a rate limit, and the OAuth `error` for the token endpoint, such as `invalid_client`.
- Each pack holds the collector's build file, `artifacts/okta.collector-build.json`, with its schemas and its trace map. The map, `docs/schema/trace-map.json`, links each field to the calls and the code behind it. `make trace-map` rewrites it, and CI fails when the committed map is stale.
- `make conformance` runs the conformance harness at the epack version go.mod pins.
- The docs list `okta.users.read`, not `okta.authenticators.read`, as the scope for each user's factor list.
- Okta's own Admin Console, Dashboard and Browser Plugin apps are left out of the app counts and percentages. Only a Super Admin can see them, so the counts changed with the collector's admin role. API service apps are left out too, since no one signs in to them. An API service app is an OpenID Connect app whose only grant type is `client_credentials`. This changes `posture.sso_coverage`, the counts and percentages in `apps`, and `app_security` in `okta.idp-posture.json`. Each of these apps counted as using SSO, so SSO coverage can drop. `apps.inventory` still lists these apps, and an API service app's row has `type` `SERVICE` and `sso_configured` false.
- `org_settings.self_service_recovery_enabled` follows Okta's order for password policies and rules. Each person gets the first rule that matches them in their first matching password policy. Before, any active rule that allowed recovery made the flag true, even a Default Rule that applied to no one because a higher policy or rule matched everyone first. The flag can now read false for such orgs. It is left out with a gap when the user list or a policy group's members cannot be read.
- In `policy.policies`, a policy that includes the built-in Everyone group has `scope_summary` `everyone`. Okta's default policies include that group, and they read `group-assigned` before. When the group list cannot be read, the scope summary of a policy that includes groups is left out with a gap.
- At internal, `group_mapping_count` in `identity_providers.inventory` counts the groups in Okta's filter allowlist for an identity provider whose group action is `APPEND` or `SYNC`. It read 0 for those before.
- At internal, a location with a region in `network_zones.inventory` has the country code once, as `US-CA`. Okta's region value already starts with the country code, so it read `US-US-CA` before.
- `org_domain` in both artifacts is the org's host, such as `acme.okta.com`. Before, it was the config value as typed, such as `https://Acme.okta.com/`.
