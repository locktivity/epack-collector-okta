# Changelog

## Unreleased

- Each percentage, and each of `policy.mfa_required_all` and `device_access.managed_device_required_for_admins`, has the count it is computed from beside it, at every level: `posture.mfa_enrolled_users_count`, `posture.mfa_phishing_resistant_users_count`, `users.password_expired_count`, `users.locked_out_count`, `users.inactive_count`, `users.suspended_count`, `apps.sso_count`, `apps.provisioning_enabled_count`, `apps.deprovisioning_enabled_count`, `privileged_access.privileged_mfa_enrolled_count`, `privileged_access.privileged_phishing_resistant_count`, `policy.mfa_required_users_count` (the count behind both `mfa_required_coverage_pct` and `mfa_required_all`), `device_access.managed_device_required_users_count`, and `device_access.managed_device_required_admins_count`. A count is null, with its percentage's gap, whenever its percentage is left out, and 0 over a population of 0, where the percentage is null.
- The schema names each percentage's count with `x-epack-numerator` and its rounding with `x-epack-rounding: floor`, so the SDK checks that every percentage is `floor(100 × count ÷ population)`. The status-based user counts, the SSO and provisioning app counts, `users.total_count`, and `apps.total_count` name the inventory rows they count, and the output check recounts them at audit and internal unless the inventory was cut short.
- At internal, each row of `users.inventory` and `privileged_access.inventory` has `has_active_mfa` and `has_phishing_resistant_mfa`, which restate the person's factor list. They are left out, with a gap, when the person's factors could not be read. Audit-level rows are unchanged, and carry no per-person MFA status.
- The collector result lists the run's 14 steps, from `sign_in` to `org_settings`, with the calls each one made. A trust run has the first six: `sign_in`, `people`, `apps`, `admin_roles`, `policies`, and `device_assurance`. Each step prints its title as the run's status line.
- `signed_in_as` records the sign-in method, `private_key_jwt` for a service app or `api_token`, and for a service app the scopes it requested, as `requested_scopes`, and `read_only: true`, since the token carries only the read scopes the collector asks for.
- A `permission_denied` gap names the scope to grant, as `missing_permission`, when the service app asked for it and Okta did not grant it. A refusal with the scope granted names no scope, and its warning now says the service app needs an admin role that can read the surface. A refusal under an API token names no scope, and its warning names the token owner's admin role. The 403 warnings in `diagnostics.warnings` change to match, including those for API tokens, admin-role assignments, and custom admin roles.
- Every gap carries the warning the collector wrote for it, shown at audit and internal, and names the call that left the value out, by `operation` and `call`, and the line that recorded it, as `source`. Errors the Okta client builds from a response, such as a body it cannot decode, name that response's call too.
- The result's request rows carry Okta's `errorCode` for each failed response as `vendor_code`, such as `E0000047` for a rate limit, and the OAuth `error` for the token endpoint, such as `invalid_client`.
- Each pack holds the collector's build file, `artifacts/okta.collector-build.json`, with its schemas and its trace map. The map, `docs/schema/trace-map.json`, links each field to the calls and the code behind it. `make trace-map` rewrites it, and CI fails when the committed map is stale.
- `make conformance` runs the conformance harness at the epack version go.mod pins.
- The docs list `okta.users.read`, not `okta.authenticators.read`, as the scope for each user's factor list.
